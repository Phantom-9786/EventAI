Build understanding in order

From basics to deep questions.

Difficulty and importance are different. Learn the foundations first, then practise the project’s hardest correctness problems.

1

Explain the product

People → screens → API → database. Describe who the project serves and what each role can do.

2

Understand a normal request

JavaScript, TypeScript, HTTP, React, Next.js and Express. Follow browsing before checkout.

3

Protect identity and data

Relations, SQL, validation, login, roles and ownership. Explain what the server must check.

4

Handle competition and money

Transactions, the final-ticket race, duplicate requests, payment verification and expiry.

5

Explain useful AI

Intent, filters, embeddings, retrieved text, context budgets and honest fallback behaviour.

6

Defend your decisions

Deployment, CI, caching, failure modes, monitoring and when another design would fit better.

Quick understanding checks

Does TypeScript validate a request from the internet?

No. TypeScript checks development-time types. Runtime schemas validate unknown incoming data; authorization and database constraints protect different rules.

Can two people both buy the final ticket?

A separate read followed by an unconditional write would be unsafe. EventPoint conditionally decreases available stock inside a transaction, and checks whether the write succeeded.

Does Groq receive only embedding numbers?

No. Vectors help match records and passages. Relevant text and structured facts provide useful context for the language model.

Does a green GitHub check prove the website is healthy?

No. CI checks a code revision. Deployment and runtime health are separate observations.

Is the BullMQ worker running booking expiry?

The worker entry point is scaffolding with no registered processors. The current API has an in-process expiry scheduler.
