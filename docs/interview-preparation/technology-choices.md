# What we use, where, and why

**How to read the last column:** these are defensible engineering tradeoffs inferred from the current implementation and project needs. They are not evidence that every alternative was historically evaluated. Versions below identify the main stack; inspect package manifests/lockfile for exact resolved versions.

| Technology / approach | What it does here | Source starting point | Common alternatives | Why this fits; what the alternative offers |
|---|---|---|---|---|
| TypeScript | Shared types across UI, API and packages | `apps/web/src/lib/api.ts`, package manifests | JavaScript; a different backend language | Typed contracts help refactoring. Types disappear at runtime, so incoming data still needs validation. Plain JS reduces type setup but loses compile-time checking. |
| Next.js 14 App Router + React 18 | Routing, layouts, server page loading and interactive client components | `apps/web/src/app/layout.tsx`, `app/page.tsx` | React + Vite; Remix; Angular | Integrated page rendering and routing fit a browsable event catalog. Vite is attractive for a browser-only SPA; it is not an inferior choice for every app. |
| React hooks and context | Local UI state, auth state and shared pending counters | `components/auth/auth-provider.tsx`, `components/admin/pending-counts.tsx` | Redux Toolkit; Zustand; TanStack Query | Current state is mostly local or small shared contexts. Redux/Zustand can organise more complex shared state; a query library can formalise server-state caching and invalidation. Context is not a full query cache. |
| Tailwind + shared CSS variables | Responsive layout, colour tokens, surface layers and reusable controls | `app/globals.css`, `app/light-surfaces.css`, `tailwind.config.ts` | CSS Modules; styled-components; Material UI | Utility styles coexist with custom product CSS. A component framework supplies more ready-made patterns but also brings its own conventions. |
| Node.js + Express | HTTP server, middleware, REST routes and feature controllers | `apps/api/src/main.ts`, `src/express/app.ts` | NestJS; Fastify; Django; Spring Boot | Express keeps the HTTP layer explicit and small. Nest offers more enforced conventions; Fastify offers a different plugin/schema approach. Current source uses Express even where classes retain decorator-like helper syntax. |
| Modular monolith | Feature separation inside one API deployment | `apps/api/src/modules` | Microservices | Keeps transactions and deployment understandable at this scale. Microservices enable independent ownership/deployment, but introduce network failures, service coordination and distributed data concerns. |
| REST + JSON | Frontend/backend request contract | `apps/api/src/express/modules`, `apps/web/src/lib` | GraphQL; tRPC; gRPC | Explicit feature endpoints fit the clients here. GraphQL supports flexible client selection; tRPC offers tightly coupled TS inference; gRPC fits other internal service contexts. |
| Zod | Runtime input validation and shared schemas | `packages/validation/src` | Joi; Yup; JSON Schema/Ajv | One TypeScript-friendly schema layer can validate unknown input. Runtime validation complements types rather than replacing authorization or database constraints. |
| PostgreSQL | Authoritative relational data, transactions, constraints, full-text search and embedding arrays | `packages/database/prisma/schema.prisma`, migrations | MySQL; MongoDB | Events, bookings, ticket types and payments form a relational model. MySQL is a credible relational alternative. MongoDB also supports multi-document transactions; the reason here is relational fit and query requirements, not an inability to transact. |
| Prisma | Typed database access, schema/migrations and transactions | `packages/database`, API services | Drizzle; TypeORM; raw SQL | Helps navigate related records while retaining parameterized SQL for FTS and ranking. Raw SQL offers direct control but more manual mapping; ORM use does not remove the need to understand SQL. |
| PostgreSQL FTS + server pagination | Keyword discovery, filtering and ordered result pages | `modules/events/events.service.ts` | Elasticsearch; OpenSearch; Algolia; Meilisearch | Reuses the database for current catalog needs. A dedicated search service can add richer relevance operations but needs indexing, freshness handling and another system to operate. |
| Redis + ioredis | Public-read TTL caches and shared AI rate/concurrency protection | `common/cache/cache.service.ts`, `express/middleware/ai-guard.ts` | In-process Map; Memcached; database-backed controls | Shared state can span API instances. An in-memory Map is simpler but instance-local. Redis is not the authority for booking prices or inventory. Public caches can degrade gracefully; AI protection deliberately has different failure behaviour. |
| Conditional database updates + transactions | Inventory reservation and guarded booking transitions | `modules/bookings/bookings.service.ts` | Explicit row locks; optimistic versioning; queue-based serialisation | The stock condition is part of the write, so concurrent buyers cannot both consume the final unit. Other approaches can also be correct; compare contention, retries and operational complexity. |
| Razorpay integration | Provider orders, checkout verification, webhook handling and refund lifecycle | `modules/payments/payments.service.ts`, booking widget | Stripe; Cashfree; PayU | INR-oriented event checkout fits the integration. Provider choice depends on supported markets, onboarding and product requirements. Do not claim test/demo payments are real captured customer revenue. |
| JWT + rotating refresh sessions + Argon2id + Google OAuth | Account authentication, refresh and password protection | `modules/auth`, browser auth client | Server-session cookies; managed auth such as Auth0/Clerk | Explicit auth demonstrates session and ownership rules. Managed auth reduces custom lifecycle work; opaque sessions are a valid alternative. The current system already uses database session state, so it is not fully stateless. |
| Cloudinary | Organizer uploads, category covers and hosted image delivery | `modules/events/event-media.service.ts` | S3 + CloudFront; ImageKit; Supabase Storage | Media is kept outside the API filesystem. Object storage offers greater infrastructure control but needs a delivery/processing design. Multiple configured providers still require consistent ownership and asset tracking. |
| Brevo HTTP API | Verification codes, password reset and transactional notifications | `modules/notifications/notifications.service.ts` | Amazon SES; SendGrid; Resend | A hosted mail service avoids operating an SMTP server. Delivery still needs sender/domain configuration, retry handling and user-visible failure states. |
| Groq + application orchestration | Intent interpretation, response generation and model-profile routing | `modules/ai/ai.service.ts`, `model-router.ts`, `groq-key-pool.ts` | Other hosted LLM providers; self-hosted models | Existing integration centralises budgets, retry policy and grounded output handling. Switching providers would require evaluating quality, latency, cost, tool support and failure behaviour; the repository alone cannot prove one provider is universally best. |
| Transformers.js + pretrained MiniLM | Local semantic embeddings for event and passage retrieval | `modules/ai/semantic-retrieval.service.ts` | Hosted embedding APIs; larger local encoders | Local CPU inference avoids per-embedding external API calls but brings model download, cold-start, CPU and memory costs. Local does not mean computationally free. |
| PostgreSQL arrays + similarity SQL | Store and compare current catalog vectors | `EventSemanticEmbedding` model; event search | pgvector with an index; Qdrant; Pinecone; Weaviate | Keeps the current small catalog in one database. Exact scanning is simpler but does not have the scaling behaviour of approximate indexed vector search. pgvector is an extension, not something already used just because PostgreSQL holds vectors. |
| Custom hybrid RAG | Combine business filters, semantic retrieval, lexical passage selection and bounded prompt context | `retrieval-context.ts`, `semantic-retrieval.service.ts`, `ai.service.ts` | Keyword-only search; full-catalog prompts; LangChain/LlamaIndex orchestration | Custom code makes this small workflow explicit. Orchestration libraries can supply connectors and common patterns, but are not prerequisites for RAG. RAG retrieves evidence; it does not fine-tune the model or remove token limits. |
| QR data + browser scanning | Present tickets and read them at admission | `app/dashboard/scan/page.tsx`, booking/payment ticket generation | Barcode; manual booking lookup; native scanner | A QR is convenient to transport an identifier. Backend authorization and ticket status checks determine admission; possessing a readable QR alone does not establish permission. |
| Custom React/CSS dashboard charts | Axes, counts and hover/tap/focus details | `components/approved/dashboard-chart.tsx` | Recharts; Chart.js; ECharts | Current charts need a small set of interactions. A library becomes useful for richer plots, zooming or larger datasets. Do not claim the project uses a chart library it does not import. |
| Jest + integration tests + GitHub Actions | Automated regressions, database checks and build checks | `apps/api/**/spec.ts`, `.github/workflows/ci.yml` | Vitest; other CI providers; browser E2E tooling | Existing tests cover backend logic and PostgreSQL-backed scenarios. Test-tool installation does not establish complete browser coverage. CI success is distinct from service deployment and production correctness. |
| npm workspaces + Turborepo | Shared packages and dependency-aware task orchestration | root `package.json`, `turbo.json` | pnpm workspaces; Nx; separate repositories | A monorepo keeps shared contracts and app changes together. It adds task/build coordination; it does not automatically mean microservices or one deployed process. |
| Vercel + Render + Neon + custom DNS | Frontend/API/database hosting and the public domain | deployment setup, `docs/deployment.md` | AWS/GCP/Azure; Fly.io; Railway; VPS | Managed hosting suits the portfolio deployment. More infrastructure control brings operational responsibility. Build-time public variables, CORS, TLS, cold starts and database connection limits remain relevant. |
| Optional Sentry + structured logging | Error capture with sensitive-data scrubbing and request correlation | `apps/api/src/config/sentry.ts`, web Sentry config | OpenTelemetry + backend; other error trackers | The integration exists; enabled collection depends on configuration. Logs and traces answer different questions, and sensitive data should not become a debugging shortcut. |

## Present but not a completed production path

| Item | Accurate interview statement |
|---|---|
| BullMQ worker app | Queue names, Redis connection and worker bootstrap exist. No job processors are registered in its entry point. |
| Booking expiry | Runs through a scheduler in the API process, with guarded database transitions. Do not attribute it to the BullMQ skeleton. |
| Socket.IO | An older ADR discusses it. The inspected current UI uses HTTP fetching/polling; do not claim deployed real-time sockets. |
| Docker files | Deployment/container configuration exists. Having files is not evidence that every production component is run with Docker. |
| Playwright dependency | Availability of a browser-test tool is not proof of a complete maintained E2E suite. |

## A useful answer pattern

“We used **X** for **this requirement**. **Y** was a reasonable alternative. At our current scope, **this tradeoff** made X suitable. If **a specific requirement changed**, I would measure **these signals** and reconsider Y.”

Avoid answers such as “MongoDB cannot do transactions,” “JWT makes everything stateless,” “Redis prevents all race conditions,” or “RAG means the LLM receives only vectors.”
